# NETCITY — RECOVERY & ITVR TEST MATRIX v0.1

**Статус: APPROVED DESIGN INPUT / PLANNED TESTS**  
**Область:** Recovery Council, Recovery Ceremony Protocol, ITVR Bootstrap & Trust Recovery.  
**Назначение:** формализовать проверяемые условия для будущей реализации и независимой проверки.  
**Граница:** этот документ описывает проектные испытания. Он не является тестовым кодом, отчётом о запуске или доказательством реализации.

## 1. Область и связанные спецификации

1. [Recovery Council Specification](RECOVERY_COUNCIL_SPEC.md) — Root Custody C1–C5, Independent Recovery Council R1–R5, Root Governance и Hybrid Anchor.
2. Recovery Ceremony Protocol v0.1 — жизненный цикл восстановления, Freeze, Manifest Validation, Evidence, Quorum, Reconstitution и восстановление управления.
3. ITVR Bootstrap & Trust Recovery v0.1 — Genesis Ceremony, DKG, FROST 2-of-3, Anti-Sybil, Hybrid Anchor, IV rotation и восстановление реестра.

Все проверки должны учитывать границы между этими контурами. Утверждённая архитектура не означает реализованный Rust-код, криптографию, аппаратную интеграцию или production deployment.

## 2. Общая модель результатов

Каждая проверка возвращает одно из трёх решений:

- `ALLOW` — все обязательные проверки успешны.
- `DENY` — выявлено нарушение, запрещённое действие или недопустимое доказательство.
- `INDETERMINATE` — доказательств недостаточно либо проверка не может быть надёжно завершена.

`INDETERMINATE` никогда не преобразуется в `ALLOW` автоматически.

Формальный принцип:

`ALLOW iff every required check is VALID`

Общие инварианты:

1. Статус участника сам по себе не выдаёт полномочия.
2. Кворум считается по уникальным действующим участникам и допустимым доменам независимости.
3. Повторные голоса одного участника не увеличивают кворум.
4. Замороженные, отозванные, просроченные или не подтверждённые участники не учитываются.
5. Порог не снижается из-за недоступности участников.
6. Owner Confirmation, техническое заключение и Council Quorum — независимые условия, если все они требуются конкретной процедурой.
7. Криптографически корректная подпись не доказывает безопасность или допустимость решения.
8. Критические переходы имеют проверяемую Audit / Provenance запись.
9. Evidence привязано к конкретным Recovery ID, Manifest version/hash, package digest, phase, action, challenge и сроку действия.
10. Неизвестные, отсутствующие или непроверяемые обязательные данные не дают разрешения.
11. Невозможность подтвердить доверенное состояние приводит к безопасному отказу и сохранению защитной блокировки.
12. Архитектурные сценарии имеют статус `PLANNED`, пока их реализация и фактическое выполнение не подтверждены отдельно.

Все участники должны подтверждать один и тот же канонический digest:

`H = Hash(CanonicalSerialize(RecoveryPackage))`

В digest должны входить как минимум: `recovery_id`, Manifest reference/version/hash, Trigger Evidence, Assessment Evidence, состав участников, предлагаемые изменения, commitment нового корня, новый Manifest hash, Anchor Transition, challenge, срок действия, phase и action.

Изменение любого подписываемого поля делает ранее собранные подписи непригодными для изменённого пакета.

При замене участника старые доли не копируются. Предпочтительная проектная процедура — новая DKG-конфигурация, новый групповой публичный ключ, отзыв старой конфигурации и независимая проверка новой панели.

## 7. Adversarial Testing

Отдельные классы атак, которые должны иметь конкретные воспроизводимые тест-кейсы:

1. **Quorum Forgery:** повторные подписи одного участника выдаются за кворум — ожидается отказ.
2. **Sybil Organization:** несколько формально разных участников контролируются одним субъектом — ожидается отказ.
3. **Manifest Rollback:** возврат старой версии после ротации — ожидается отказ.
4. **Evidence Replay:** повторное использование подписи, nonce или Recovery Evidence — ожидается отказ.
5. **Compromised R4:** R4 пытается блокировать независимую замену или выдать ложное заключение — ожидается независимая процедура и fail-closed при недостатке доказательств.
6. **Compromised IV Panel:** компрометация двух долей или общего домена контроля — ITVR замораживается.
7. **Genesis Substitution:** подмена исходного Manifest до закрепления fingerprint — Genesis не активируется.
8. **Authority Escalation:** Architect, Agent или администратор пытается единолично изменить Trust Policy — KVP Authorization Gate запрещает действие.

## 8. Property-Based Testing

Будущие property-based тесты должны генерировать произвольные последовательности событий и проверять инварианты:

| ID | Генерируемое свойство | Обязательное условие |
|---|---|---|
| PROP-001 | Произвольные последовательности событий Recovery | Нельзя обойти обязательные состояния |
| PROP-002 | Произвольное количество повторных голосов одного участника | Кворум не увеличивается |
| PROP-003 | Разные комбинации отозванных/замороженных участников | Недопустимый кворум не формируется |
| PROP-004 | Любые изменения Recovery Package | Старые подписи не действуют на новый digest |
| PROP-005 | Любые последовательности версий Manifest | Монотонность не нарушается |
| PROP-006 | Любые переходы состояний R4 | `R4_PENDING` не подписывает Attestation |
| PROP-007 | Любые изменения `org_id` и evidence независимости | Не создаётся искусственная независимость |
| PROP-008 | Любые сбои во время восстановления | Нельзя получить ложный `ROOT_CONTROL_RESTORED` |

## 9. Fault Injection

Будущая тестовая среда должна моделировать:

- внезапное отключение питания;
- потерю сети;
- потерю/отказ HSM;
- повреждение Audit-записи;
- частичную запись Manifest;
- отказ одного verifier;
- отказ двух verifier;
- сбой во время DKG;
- повторную доставку и перестановку сообщений;
- параллельное выполнение конфликтующих операций;
- восстановление старого snapshot;
- повреждение локального состояния после успешной подписи.

Ожидаемое поведение: либо безопасное завершение полностью подтверждённой операции, либо безопасная остановка. Частично завершённая церемония не должна активировать Root или снимать Freeze.

## 11. Acceptance Criteria

Этап будущей реализации не считается завершённым, пока не выполнены и не подтверждены:

- **AC-01:** все обязательные переходы Recovery state machine проверены.
- **AC-02:** Council 3-of-5 и IV Panel 2-of-3 проверяются независимо.
- **AC-03:** повторные голоса одного участника не формируют кворум.
- **AC-04:** Anti-Sybil проверяет фактические домены контроля.
- **AC-05:** Replay и подмена Recovery Package блокируются.
- **AC-06:** Manifest rollback блокируется.
- **AC-07:** Freeze нельзя снять без независимой валидации и отдельного разрешения KVP.
- **AC-08:** R4_PENDING не может подписывать Attestation.
- **AC-09:** потеря/компрометация IV не снижает порог.
- **AC-10:** невозможность подтвердить Genesis приводит к безопасному отказу.
- **AC-11:** каждое критическое решение имеет проверяемую Audit-запись.
- **AC-12:** Fault Injection не приводит к ложному восстановлению Root.
